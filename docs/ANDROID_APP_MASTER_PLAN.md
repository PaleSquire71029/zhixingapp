## 0. 本文的用途与执行规则

这份文档是知行 Android App 项目的长期主规划，用于跨对话、跨开发阶段保存产品边界、技术决策、旧项目结构、迁移顺序、接口约束和验收标准。

后续任何开发都应先阅读本文及同目录的实施状态文件，不能只依赖聊天上下文或模型记忆。

### 0.1 用户已经明确的要求

1. **只做 Android 端**。本项目不规划 iOS、桌面端或 Web 版 App。
2. 把知行计算器与知行AI整合为一个应用。
3. 最大程度借鉴 iOS 26 Liquid Glass 的材质、折射、光影、空间感和触摸反馈。
4. 视觉仍然要有知行自己的设计气质，不能把 Apple 界面、图标或品牌直接照搬。
5. **完全重新设计 App 界面**，不是给旧网页套一层壳，也不是把网页缩小放进手机。
6. **逐步迁移原有功能**，每个阶段都需要有测试和验收，不能因重做界面丢失原有功能。
7. App 工程与新文件统一放在本仓库，不要把新 App 的文件散落到 calculator 或 zhixing_ai 仓库。
8. 旧仓库只作为原功能、算法、接口、数据结构、字体与测试的参考来源。未经明确要求，不为 App 开发而破坏旧网页项目。
9. 普通计算功能必须本地可用，不得擅自给普通计算器增加强制账号登录。
10. 视觉采用浅色体系；不增加深色模式，也不在浅色页面中放置大块深色面板。
11. 计算准确性、公式清晰度、响应速度和数据安全优先于装饰效果。

### 0.2 规划约束

- 所有未核实的线上配置、接口可用性、模型服务状态都必须标记为“待验证”。
- 历史需求不等于当前功能已经实现。
- 开源库的 README、版本号、许可证、最低 Android API 和发布制品必须在正式引入前重新核实。
- 不能把 API Key、Cloudflare Token、Supabase service-role key、数据库密码、管理员密码或签名私钥提交到仓库。
- 不得为了让页面看起来能运行而用假数据、假余额、假模型列表或虚构成功状态。
- 不允许用 WebView 承载整个 App。公式、导航、键盘、对话和计算页面均以原生 Compose 实现为目标。
- 如果个别内容需要临时兼容旧数据格式，必须有明确迁移边界和移除条件，不能让旧网页成为新 App 的长期 UI 依赖。

### 0.3 需求优先级

发生冲突时按以下顺序处理：

1. 用户最新明确指令；
2. 本文中“已确认的产品要求”；
3. 当前实际代码、接口与数据库约束；
4. 本文中的技术建议；
5. 旧聊天中的历史尝试与未验证设想。

### 1.4 已发现的 AI 产品 ID 重要问题

在 calculator 仓库的 ai-proxy/src/index.js 中，当前代码有如下逻辑：

    function normalizeAppId(value) {
      return value === "zhixing-ai" ? "zhixing-ai" : "learning";
    }

这意味着传入 zhixing-ai 时会保留 zhixing-ai，其他值会归一化成 learning。

但是 ai-calculator.html 发送的 AI 场景标识是 calculator-ai。Worker 中虽然已经存在 calculator-ai 的提示词分支，但这段 normalizeAppId 逻辑可能会让 calculator-ai 被映射到 learning，导致提示词和产品场景不按预期隔离。

此外，当前 cloud-chat-storage.sql 的 app_id CHECK 约束只允许：

- zhixing-ai
- learning

并不包含 calculator-ai。

**结论：新 App 开始对接计算器 AI 云端能力前，必须先设计并验证产品 ID 和数据隔离迁移。** 不允许只改客户端 app 字段来假定后端已经支持。

建议未来明确三个服务端场景标识：

- zhixing-ai：独立知行AI主对话；
- calculator-ai：计算器内的 AI 分析/解题对话；
- learning：知行AI学习版，当前不属于本 App 第一版范围，但需保护其既有数据和行为。

三个场景可以在 App 的统一“最近对话”页面合并展示，但后端产品身份、提示词、权限和历史数据必须保持可区分。

## 2. 产品范围和边界

### 2.1 第一版 App 包含

1. 知行计算器的本地计算能力；
2. 知行AI主产品的原生聊天能力；

- iOS、iPadOS、macOS、Windows、Linux 或 Web App；
- 把知行AI学习版完整嵌入 App；
- 复制旧网页导航站或旧管理后台；
- 将后台模型密钥、管理密码或 Cloudflare 管理操作放进 App；
- 将普通计算器设置为必须登录；
- 使用 WebView 承载整页 UI；
- 在没有接口依据时伪造实时搜索、模型余额、Token 统计或文件处理能力。

- 计算：本地优先，离线可用。
- 知行AI：联网使用 Worker / 模型服务，账号与云历史按后端要求启用。
- 计算器 AI 分析：由计算器发起，自动提供当前页面、输入和计算结果，不要求用户复制粘贴；在服务端以 calculator-ai 场景隔离。
- 历史：本地计算记录与云端 AI 会话在一个界面中管理，但标记来源、类型和同步状态。
- 设置：只提供用户可用的 App 设置；管理员管理能力继续放在受保护的后台。

## 3. 总体技术路线

### 3.1 技术决策

| 层 | 推荐技术 | 说明 |
|---|---|---|
| 主语言 | Kotlin | Android 原生开发 |
| UI | Jetpack Compose | 页面、键盘、弹窗、列表和状态 |
| 基础设计组件 | Material 3 Foundation + 自定义组件 | 只使用必要基础设施，不沿用默认 Material 外观 |
| 架构 | 分层架构 + MVVM / 单向数据流 | UI State、事件、UseCase、Repository 分离 |
| 并发 | Kotlin Coroutines + Flow | 网络流、数据库观察和 UI 状态 |
| 本地数据库 | Room | 计算历史、收藏、离线数据 |
| 设置存储 | DataStore | 偏好、界面设置、功能开关 |
| 网络 | OkHttp + Kotlin Serialization | Worker JSON、SSE 流式响应、超时和取消 |
| 图片 | Android Photo Picker / CameraX | 选择图片和拍摄；按实际功能接入 |
| 公式 | 原生 Compose LaTeX 渲染组件候选 | 不依赖整页 WebView |
| 图表 | Compose Canvas / 自绘图层 | 与函数域模型分离 |
| 着色器 | AGSL RuntimeShader + RenderEffect | API 33+ 完整路径，低版本降级 |
| 凭据 | Android Keystore 保护的加密存储 | 保护会话 Token；不保存服务端密钥 |
| 测试 | JUnit、Compose UI Test、Android Instrumented Test | 计算、数据、界面和设备测试 |
| CI | GitHub Actions + Gradle | 自动编译、单测、Lint、构建 APK |

### 3.2 Android 版本策略

- AGSL RuntimeShader 从 Android API 33 开始提供；它能按像素执行用户定义的 Android Graphics Shading Language 着色函数。
- Android API 31 及以上可使用 RenderEffect 等图形效果作为一部分降级基础。
- 更早版本使用轻量半透明材质、静态高光和简化阴影，不模拟不存在的实时折射能力。
- **建议初始最低版本暂定 API 26，最终 minSdk 必须在首轮依赖兼容性核验和目标手机测试后确定。**
- compileSdk / targetSdk 在创建工程时选择当时稳定且兼容的 Android SDK 版本；不要在规划文件中长期锁死一个会过时的版本号。
- API 33 以下不应通过 CPU 每帧生成全屏位移贴图来假装完整玻璃，这会增加发热、掉帧和耗电风险。

官方资料：

- [Android RuntimeShader API](https://developer.android.com/reference/android/graphics/RuntimeShader)
- [Android 官方 AGSL 使用指南](https://developer.android.com/develop/ui/views/graphics/agsl/using-agsl)

### 3.4 分层职责

- app：启动、Application、主 Activity、导航根、系统栏、依赖装配。
- core/common：时间、ID、错误类型、日志脱敏、通用扩展。
- core/model：跨模块的数据结构和状态类型。
- core/design：颜色、字体、间距、图标、圆角、基础组件。
- core/glass：背景采样、Shader、折射、材质参数、性能档位和无障碍降级。
- core/network：Worker API、SSE、超时、重试、网络错误模型。
- core/auth：登录、刷新、登出、账号状态和安全凭据存储。
- core/database：Room 实体、DAO、Migration。
- core/datastore：用户偏好和非敏感配置。
- domain/math：表达式解析、精确数值、方程、不等式和函数域规则。
- domain/chemistry：配平、化学式解析、反应规则和守恒校验。
- domain/assistant：AI 场景、上下文构建、消息 ID、请求状态机。
- feature：各自的 ViewModel、UI State、Composable 和导航入口。

## 4. 知行视觉系统

### 4.1 设计定位

暂定名称：**知行 Light Liquid**。

核心关键词：

- 轻透；
- 冷静；
- 理性；
- 清晰；
- 有光学层次；
- 操作具有物理反馈；
- 具有知行品牌识别，而不是 Apple UI 的复刻品。

### 4.2 色彩原则

- 全应用只采用浅色主题；
- 主背景以珍珠白、柔和浅银、极淡冷蓝为基础；
- 使用少量知行原有强调色作为焦点色；
- 重要计算结果用高对比度文本；
- 玻璃表面不能降低文字对比度；
- 错误、成功、警告颜色需要同时配合图标和文本，不只依靠颜色；
- 不使用大块黑色、深灰色或深色卡片填充浅色页面。

颜色的最终 RGB / HSL 数值将在设计系统阶段按真机亮度、色彩对比和截图测试确定，不在本阶段凭空锁定。

### 4.3 字体原则

- 中文：选择经过授权且 APK 体积合理的字体资源；OPPO Sans 作为候选品牌字体，使用前先核实授权与文件处理方式。
- 数字 / 表达式 / Token 数据：JetBrains Mono 或等宽数字字体。
- 公式字体：优先采用公式渲染库配套数学字体；数学符号不能因中文字体缺字而显示方框。
- 字体加载必须有系统回退，不得卡在永久加载状态。
- 字体大小适配系统显示缩放和无障碍字号。

### 4.4 形状、布局与动效

- 使用连续曲率圆角，避免所有组件看起来像同一尺寸的网页卡片；
- 通过材质高光、边缘和层次建立空间，不使用重阴影堆叠；
- 页面滚动、输入和键盘出现时不跳动、不遮挡内容；
- 触摸区域满足 Android 常用最小点击尺寸；
- 尊重系统的减少动态效果偏好；
- 不让整个背景持续高频动画；
- 动画有开始、结束和取消状态，不能阻碍快速输入和连续操作。

### 4.5 玻璃材质使用边界

液态玻璃优先用在：

- 底部主导航；
- 顶部轻量工具栏；
- 短操作菜单；
- 浮动操作按钮；
- 小型工具切换器；
- 少量弹出面板；
- 需要强调的输入控件。

不建议用在：

- 整页内容背景；
- 长篇 AI 回答正文；
- 复杂计算步骤；
- 数学公式底板；
- 密集键盘每一个按键；
- 高密度表格和历史记录正文。

内容主体始终保持高对比、可读、稳定。玻璃是操作层，不是内容层。

## 5. 液态玻璃技术方案

### 5.1 目标效果

完整材质由以下视觉因素组合：

1. 背景采样：玻璃后方显示真实内容，而不是单纯透明色。
2. 动态模糊：以合理半径模糊后方画面，保留一定颜色与结构。
3. 透镜折射：根据玻璃轮廓、边缘距离和法线，对背景采样坐标作位移。
4. 轻微色散：边缘局部出现细小 RGB 位移，强度必须受控。
5. 镜面高光：根据模拟光源和玻璃表面方向产生边缘高光。
6. 环境反射：玻璃能反映背景主色和局部亮度变化。
7. 触摸形变：按下、拖动、切换时高光与折射产生轻微响应。
8. 形状融合：底部导航活动区域平滑移动，而不是普通硬切换。

### 5.2 候选开源项目

以下是截至 2026-10-31 进行过的仓库初步检查。Stars、提交时间和版本都会变化，正式依赖前重新核验。

参数至少应覆盖：

- 容器尺寸；
- 圆角半径；
- 折射强度；
- 折射深度；
- 模糊半径；
- 边缘亮度；
- 高光方向；
- 环境色；
- 色散强度；
- 触摸进度；
- 按压形变量；
- 渲染分辨率比例；
- 对比度保护；
- 当前材质质量档位。

参数需限制上下界，避免极端输入让 shader 出现过亮、过暗、边缘断裂或画面闪烁。

### 5.5 质量档位与降级策略

| 档位 | 适用情形 | 内容 |
|---|---|---|
| Premium | API 33+ 且设备 GPU/帧率预算允许 | 实时背景采样、AGSL 折射、克制的色散、高光和触摸形变 |
| Standard | GPU 性能一般或温度升高 | 降低采样分辨率、折射强度、模糊半径和刷新频率 |
| Lite | API 33 以下或设备不支持完整路径 | 静态半透明、轻量模糊（可用时）、渐变和高光，不模拟完整实时折射 |
| Off | 用户关闭动态材质或系统减少动态效果 | 普通浅色表面，不影响导航和操作功能 |

### 5.6 性能约束

- 不对整个窗口每帧做多次全屏离屏渲染；
- 优先局部采样玻璃后方的必要区域；
- 避免玻璃组件之间相互递归采样；
- 缓存 Shader 和可复用资源；
- 不在 UI 主线程进行图像处理或公式解析；
- 列表滚动时降低或暂停非必要高光动画；
- 监控掉帧、GPU 时间、内存、热状态和持续耗电；
- 若材质影响输入延迟或计算稳定性，必须自动降级；
- 必须提供关闭动态材质的路径。

### 5.7 旧网页实验的正确定位

旧 liquid-glass-test.html 使用浏览器 SVG filter / feDisplacementMap、Canvas 位移贴图和 backdrop-filter 检测，并在部分移动条件下退化为模糊、高光和渐变。它可以帮助比较折射、色散和低功耗效果，但不应被复制为 Android 方案。

新 App 应使用原生 Android 图形管线和设备 GPU 能力；测试页面只能作为视觉参考，不能证明 Android 原生效果已实现。

- 图像或题目附件（仅在用户主动提交时）；
- 用户选择的分析目标。

不能把无关页面状态、其他工具输入、隐私信息或全部本地历史打包发送。

AI 分析应返回与当前工具对应的结果结构，UI 再渲染重点和步骤。模型输出必须作为不可信文本处理，不能执行模型提供的任意脚本或 HTML。

### 8.4 模型设置

- 模型列表从 Worker 拉取，不硬编码供应商模型名称；
- 模型 ID 与显示名称分开保存；
- 当前模型必须能实际发起请求；
- 模型列表失败时显示明确错误；
- API Key 只由后台保存和使用；
- 上游余额/Token 信息只有在接口真实支持时展示；
- 不支持时明确显示“不支持或无法查询”，不能伪造为 0；
- 模型设置不应让普通用户接触管理员密钥或后端配置。

旧聊天页面有自带 API Key 模式的历史实现。是否在新 App 中保留该模式要作为独立决策：默认先使用知行 Worker；若未来开放自带 Key，只能由用户主动开启、在本机加密保存、明确告知数据会发送到用户指定供应商，并提供清除入口。绝不将用户 Key 写入日志或仓库。

## 9. Worker、账号和云端历史接入

### 9.1 网络接口

初步待核验接口：

| 用途 | 路径 | 需要验证 |
|---|---|---|
| 健康检查 | GET /health?app=... | Worker 是否在线、配置是否正确 |
| 模型列表 | GET /api/models?app=... | 返回模型 ID、默认模型和错误 |
| 对话 | POST /api/chat | JSON、流式 SSE、取消和错误处理 |
| 账号登录 | POST /api/account/login | 用户名/邮箱标识规则与返回字段 |
| 会话刷新 | POST /api/account/refresh | Refresh Token 轮换 |
| 当前账号 | GET /api/account/me | Bearer Token 验证 |
| 修改密码 | POST /api/account/password | 权限和密码策略 |
| 登出 | POST /api/account/logout | 服务端会话失效 |
| 会话列表 | GET /api/history/conversations | 用户和 app_id 隔离 |
| 新建会话 | POST /api/history/conversations | 归属和唯一 ID |
| 消息读取 | GET /api/history/messages | 会话归属校验和分页 |
| 消息写入 | POST /api/history/messages | 幂等和消息 ID |
| 会话删除 | DELETE /api/history/conversations?id=... | 用户归属和级联行为 |

新 App 的 Worker API 地址先以 https://api.zhixing.us.ci 为主候选，但必须验证线上 TLS、DNS、可用性和真实路由。旧 workers.dev 地址不能作为生产依赖写进 App。

### 9.2 原生客户端身份验证

- 原生 App 不具有可信的前端私钥，不能把静态 API Secret 打包在 APK；
- 账号登录和受保护历史请求应使用服务器返回的用户访问令牌；
- Access Token 与 Refresh Token 使用 Android Keystore 保护的加密存储；
- Refresh Token 轮换后原子更新本地凭据；
- 登出时清除本地令牌并调用服务端登出；
- 会话过期时给出明确状态，不应无限重试；
- API 错误日志不包含完整 Token、Authorization Header、Cookie 或用户消息正文；
- 不能仅通过 User-Agent 或客户端传来的 user_id 判断身份；
- 服务端必须校验 Token，使用已验证的用户身份决定数据归属；
- 原生客户端的网络请求不应依赖浏览器 CORS Origin 来证明身份；
- 不得为了 App 接入把 CORS 改成任意来源并以此替代鉴权；
- 如将来需要防滥用，可评估 Play Integrity 等附加机制，但不能将其作为唯一身份验证方式。

### 9.3 用户名登录兼容性

历史需求包含用户名唯一、用户名加密码登录。

当前网页界面有 identifier 字段，但底层 Supabase Auth 流程是否完整支持用户名映射，必须检查 Worker 现有实现和数据库字段后再确认。不能只因为 UI 写了“账号/用户名”就认为后端已支持。

接入前需要测试：

- 新用户注册；
- 用户名唯一约束；
- 大小写与空格规范化；
- 用户名登录；
- 邮箱登录（如保留）；
- 密码错误；
- 账号停用；
- 修改密码；
- Refresh Token 轮换；
- 登出；
- 不同用户之间完全隔离。

### 9.4 本地计算不强制登录

强约束：

- 计算器标准计算、科学计算、方程、不等式、函数图像、单位换算和基础化学工具可以本地使用；
- 登录窗口只能出现在用户主动进入需要账号的 AI / 云同步操作时；
- 不因未登录而隐藏或禁用本地计算能力；
- 用户取消登录后返回当前计算页面，不能清空输入；
- 云历史暂不可用时，已保存的本地记录仍可查看。

### 9.5 云端历史与本地历史

现有云端历史采用 Supabase 与 Worker：

- 数据按用户 user_id 和产品 app_id 区分；
- 消息有 client_message_id 幂等字段；
- SQL 中存在 conversation_id + client_message_id 唯一约束；
- 旧文档记录云历史保留 90 天；
- Worker 配置有定时清理任务，需要核实当前线上定时触发器与 SQL 清理函数。

新 App：

- Room 管理本地计算历史；
- 云端 AI 会话继续通过 Worker API 访问；
- 最近对话统一展示，但类型和来源可识别；
- 本地记录和云端记录使用不同的数据来源标记；
- 云端记录加载时按 conversation ID 合并；
- 消息写入使用稳定 client_message_id；
- 重试不允许创建重复消息；
- 删除前显示来源与影响；
- 离线期间的云端写入应有明确待同步/失败状态；
- 不将用户的本地全部计算历史自动上传云端；
- 保留期限、删除策略和用户隐私说明必须一致。

**数据库迁移前置事项：** 当前历史 SQL 的 app_id 约束没有 calculator-ai。扩展约束前必须备份并检查现有数据，保证旧 zhixing-ai 与 learning 记录不变。若添加 calculator-ai，要为新场景写单独迁移 SQL、权限测试和回滚方案。

## 10. 登录、隐私与数据安全

### 10.1 密钥管理

禁止提交：

- 模型 API Key；
- Cloudflare API Token；
- Supabase service-role key；
- 数据库密码；
- 管理员密码；
- JWT / Session 签名 Secret；
- APK 签名 keystore；
- 第三方服务的私密凭据。

公开 Supabase publishable / anon key 并不等于服务端密钥，但所有表仍必须配置正确 RLS；新 App 优先通过 Worker 历史 API 读写，不把服务端职责交给客户端。

### 10.2 Token 安全

- 使用 Android Keystore 保护本地加密密钥；
- Token 不写入普通 DataStore 明文；
- 不写入 logcat；
- 不进入崩溃报告；
- 不进入剪贴板；
- 不进入分析事件；
- 登出清除；
- Token 刷新失败需要重新认证；
- 设备备份行为应防止敏感 Token 被意外备份到不合适的位置。

### 10.3 隐私边界

- AI 提问内容会被发送到 Worker 配置的模型供应商；
- 图片/文件在用户主动提交后可能转发给模型供应商；
- 本地计算内容默认留在设备；
- 云端历史只保存实际选择同步的 AI 对话；
- 数据删除应分别处理本地记录和云端记录；
- 隐私声明应说明服务商、数据类型、留存范围和同步方式；
- 未经用户主动操作，不要把计算器页面所有字段、设备文件或剪贴板发送给 AI。

### 10.4 日志

允许记录必要诊断元数据：

- 请求类型；
- 状态码；
- 模型 ID（非密钥）；
- 耗时；
- 错误类别；
- 请求 ID；
- 客户端版本。

默认禁止记录：

- 密码；
- API Key；
- Access / Refresh Token；
- Cookie；
- 完整用户消息内容；
- 图片和文件原件；
- 无必要的精确位置、设备标识或个人数据。

## 15. 已知风险和处理方式

| 风险 | 影响 | 处理 |
|---|---|---|
| 玻璃 shader 设备兼容差异 | 折射显示异常或掉帧 | 先做 Glass Lab，真机测试并降级 |
| 旧计算逻辑与 DOM 耦合 | 迁移成本高、容易漏功能 | 建立 Kotlin 域层和回归测试 |
| Worker app_id 归一化错误 | AI 提示词和历史数据串场 | 接入前修正并测试后端 |
| SQL app_id 约束不包含 calculator-ai | 云端历史写入失败或错误隔离 | 单独 schema migration，保护旧数据 |
| 账号用户名规则不一致 | 登录失败或账号重复 | 核对服务端和数据库唯一约束 |
| 旧 localStorage 数据 | 用户历史无法自动出现在 App | 提供导出/导入和字段映射 |
| 字体体积过大或授权不明 | APK 过大或分发风险 | 核验授权，子集化或替代 |
| 公式渲染库覆盖不足 | AI 公式和复杂数学符号错误 | 真实样例测试后决定 |
| Native 请求与 Worker CORS/Origin 规则冲突 | Android 网络请求失败 | 设计原生认证方式，不开放任意 Origin |
| 第三方玻璃库更新或停止维护 | API 变化和构建失败 | 知行自有封装，便于替换底层 |
| AI 上游服务不可用 | 对话失败 | 清晰错误、重试、保留输入和本地计算 |

## 20. 当前结论

本项目的默认技术方向为：

- **Android 原生：Kotlin + Jetpack Compose；**
- **视觉：知行 Light Liquid，全浅色，借鉴 iOS 26 Liquid Glass 的动态材质与交互，不照抄 Apple 品牌 UI；**
- **玻璃：AGSL / RuntimeShader 为核心，Backdrop 为第一候选，先通过独立 Glass Lab 验证；**
- **计算：逐步将旧 JS 算法迁移为可测试 Kotlin 域模块；**
- **AI：继续使用受保护的 Cloudflare Worker，重建原生客户端；**
- **数据：Room 本地历史 + Worker/Supabase 云端 AI 历史；**
- **账号：原生登录，但普通本地计算不强制登录；**
- **迁移：分阶段、逐项对照、每阶段测试，不整体复制旧网页；**
- **仓库：所有新 App 文件放在 PaleSquire71029/zhixingapp。**

当前已经建立最小原生 Compose 工程骨架和四个主导航占位入口，用户图标、Gradle Wrapper 与系统窗口适配代码已加入。液态玻璃、计算器算法、AI、账号和云历史仍未迁移。本文件是长期需求和架构基线；真实实施进度以 `docs/IMPLEMENTATION_STATUS.md` 为准，详细接手步骤见 `docs/PROJECT_STATUS_AND_GUIDE.md`。

## 21. 小步开发规则（强制）

本项目采用“小步、可构建、可回滚”的开发节奏。不要把一个阶段拆成需要一次性完成数千行代码的大任务。

### 21.1 每个小步的边界

- 一次只完成一个可以独立检查的目标；
- 每个小步尽量只改动一个功能区域；
- 不同时引入 UI、算法、网络、数据库和动画多个复杂层；
- 新依赖一次最多引入一组直接相关依赖，并记录版本和许可证；
- 如果构建失败，先修当前失败，不继续叠加其他功能；
- 每一步结束后更新 IMPLEMENTATION_STATUS.md；
- 记录修改文件、提交 SHA、构建结果和仍未验证的事项。

### 21.2 第一阶段已细分的任务

| 编号 | 小步目标 | 完成条件 |
|---|---|---|
| 1 | 建立最小 Compose 工程 | 工程配置、入口 Activity 和首页存在 |
| 2 | 补齐 Gradle Wrapper | gradlew / bat / wrapper JAR 可用，CI 使用 wrapper |
| 3 | 系统栏和安全区 | 状态栏、导航栏、键盘适配正确 |
| 4 | 抽取基础设计 Tokens | 颜色、字体、圆角、间距集中管理 |
| 5 | 建立 Glass Lab 静态页面 | 不改主界面的独立实验入口 |
| 6 | 背景采样实验 | 可观察玻璃后方内容采样是否正确 |
| 7 | 模糊实验 | 单独验证模糊半径和 GPU 成本 |
| 8 | 单通道折射实验 | 一个 AGSL shader 只做背景位移 |
| 9 | 高光和轻微色散 | 分开验证高光、色散，不叠加复杂动画 |
| 10 | 触摸反馈 | 先按压，再拖动，不同时做融合 |
| 11 | 质量档位 | Premium / Standard / Lite / Off |
| 12 | 主导航玻璃化 | 只把验证过的材质应用到底部导航 |

### 21.3 计算器迁移也必须拆细

按表达式 tokenizer、parser、基础求值、科学函数、运算符优先级、方程、不等式、分母零点、函数图像、单位换算、化学配平、反应预测、本地历史和键盘顺序迁移。每一项先建立测试，再迁移实现，不一次性重写 calculator.html。

### 21.4 AI 迁移也必须拆细

按 Worker 健康检查、模型列表、普通请求、SSE 解析、停止、错误恢复、Markdown、LaTeX、图片选择、文件选择和计算器上下文传递顺序实施。

### 21.5 每个小步的完成定义

一个小步只有满足以下条件才能勾选：

1. 目标文件已提交；
2. 项目构建通过；
3. 对应测试通过，或明确记录当前环境无法执行；
4. 未实现的后续功能没有被伪装成已完成；
5. 实施状态文件已更新。

不要用“等有空再一起做”的大任务表达后续计划。每次只取最靠前的一个未完成小步。
